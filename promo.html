两个模型，谁也没法放水。

24Hagent 是一个住在 Claude Code 里的常驻编排器。它帮你拆任务、派活、独立验质量门，然后调另一个 AI（Codex）来做对抗审查——不是你平时用的那个模型，是另一个。市面上所有类似工具都是同一个模型既写又审，只有 24Hagent 用了两个模型。

唯一做跨模型对抗审查的编排器

跟别人差在哪

autobeat、baton、sisyphus、agent-fox——GitHub 上能搜到的自动编程编排器，全部是同一个模型开多个实例：一个实例写代码，另一个实例审代码。问题是，不管是 Claude 开三个、GPT 开五个，同一个模型改自己写的东西，它就是看不到自己的盲区。这不叫审查，这叫自我安慰。

24Hagent 做了件简单的事：Claude 负责写，Codex 负责审。两个模型不共享上下文，不存在串通。Codex 的审查结果经常跟 Claude 自己的判断不一样——这正是你花钱买它的原因。

一圈长这样

  1. 编排器从蓝图里拆出任务，写一份 CURRENT_TASK.md——要做啥、改哪个文件、跑哪些验收命令，全写在里面
  2. 施工队先写一个会失败的测试，再写实现。测试全绿了，交一份 WORK_REPORT.md
  3. 编排器不信施工队的自述，自己把四个质量门重跑一遍 test lint typecheck coverage
  4. 质量门全绿了，才把 diff + 测试结果 + 蓝图打包发给 Codex 审查 --sandbox read-only
  5. Codex 看完给裁决： PASS → 下一个任务 NEED_FIX → 返修，最多两次 NEED_HUMAN → 停机，等你拍板
  6. 过了就 git commit，没过就返修。你全程不需要盯着。
# 编排器独立复跑——不是问 Worker "测试过了吗"，是自己跑

powershell -NoProfile -ExecutionPolicy Bypass -File scripts/codex_review.ps1
# Codex 看完输出: PASS | NEED_FIX | NEED_HUMAN

三条死规矩

这三条是写死在脚本里的，不靠自觉。

第一条

测试是 Claude 的活，Codex 碰都不碰

施工队写测试 + 跑测试。编排器不信，自己跑一遍。Codex 只读编排器的验证报告当证据——它连测试命令都没权限执行，省额度是天然结果。

第二条

Codex 从机制上就是只读的

codex exec --sandbox read-only——这个参数掐死了写文件、跑构建、执行测试的所有路径。不是建议，是沙箱硬限制。

第三条

验收命令写死在任务包里

每份 CURRENT_TASK.md 都有一栏 acceptance_checks。施工队动手前就知道要过哪些关，编排器复跑时也不用猜，Codex 审查时照着验收。

怎么装到我的项目里

不手写 JSON，不自己建 .agent 目录，不对着空模板发呆。四步，大部分是自动的。

01

把 24hagent-starter 文件夹拷进你项目根目录

从 24Hagent 仓库里找到这个文件夹，整个拖过去。它里面有所有核心脚本、协议文件、审查标准，以及一个帮你自动安装的 skill。

02

在 Claude Code 里说一句

install 24Hagent

Claude Code 会自动检测这个文件夹，启动安装 skill：读你的 package.json 探测工具链，把文件拷到正确位置，然后开始问你问题。

03

回答两个问题

第一个：你的项目是做什么的。第二个：第一版要做哪些功能。就这两个。质量门全自动——你的项目装了 vitest 就开 test 门，装了 eslint 就开 lint 门，没装的就自动关掉并告诉你缺什么。不需要你选菜单。

04

删掉 starter 文件夹，贴启动提示词

安装完成时屏幕上会打印一段启动提示词和一句"删掉这个文件夹"。贴进去，编排器开始自己转。以后你只有在看到 HUMAN_HANDOFF.md 时才需要出现。

已经跑通了什么

我们建了一个真实的 TypeScript 小项目（日期工具库，vitest + eslint + 100% coverage），让 24Hagent 在上面跑了完整闭环。以下不是设计文档里的设想，是实际跑出来的。

✓

写了 slugify 函数，Codex 审查 PASS
四门全绿，一次过。从拆任务到 commit，中间没人碰。

✓

故意漏了一个测试，Codex 抓出来了
施工队忘了给下划线保留写测试。Codex 查 spec 时发现 DoD 写了但没测试证据，返回 NEED_FIX。补上后重审 PASS。

✓

Codex 真的用了 codegraph
不是我们让它用——它自己调了 11 次 codegraph MCP 工具，查了函数调用链、barrel export、测试 import 结构。有一轮还靠 codegraph 发现了一个纯 diff 根本看不出来的测试 bug。

✓

7 次真实 Codex 调用，0 次 mock
3 次 PASS + 3 次 NEED_FIX + 1 次 NEED_HUMAN。每次都有 raw JSONL 落盘，每次都有结构化裁决。你去看 .agent/codex-review-raw.jsonl 就能验证。
